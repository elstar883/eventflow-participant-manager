# Правила проекта EventFlow

## Карта репозитория

- `README.md` — описание проекта, быстрый старт, скриншоты и устройство;
- `app/` — готовая статическая версия приложения;
- `data/` — синтетические CSV-наборы и настройки события; только чтение;
- `references/` — бриф, критерии готовности и визуальный ориентир; только чтение;
- `docs/ARCHITECTURE.md` — архитектура и поток данных;
- `docs/DATA-MODEL.md` — модель участника, схема IndexedDB и инварианты;
- `docs/QA-CHECKLIST.md` — автоматическая и ручная проверка;
- `docs/examples/backup-sample.json` — пример резервной копии для демонстрации;
- `docs/images/` — скриншоты desktop и mobile;
- `.opencode/commands/` — команды `data-plan`, `data-build`, `data-qa`;
- `.opencode/skills/eventflow-participant-manager/SKILL.md` — повторяемая методика;
- `scripts/validate.mjs` — проверка данных, структуры и ограничений приложения;
- `.github/workflows/tests.yml` — CI на Node.js 18, 20 и 22;
- `package.json`, `Makefile` — локальные команды `check` и `serve`;
- `LICENSE` — MIT.

## 1. Язык

- Общайся с пользователем только на русском языке.
- Интерфейс, сообщения, ошибки и подтверждения приложения пиши по-русски.
- Технические имена файлов и JavaScript-сущностей можно оставлять на английском.

## 2. Источники требований

- До планирования прочитай `references/project-brief.md`.
- Критерии готовности находятся в `references/acceptance-checklist.md`.
- `references/visual-reference.png` используй как визуальный ориентир, а не как источник функций.
- `data/event-settings.json` задаёт допустимые статусы и типы билетов.
- CSV и JSON из `data/` — синтетические учебные данные.
- Если изображение противоречит текстовому брифу, главным является бриф.

## 3. Границы проекта

- Папки `references/` и `data/` доступны только для чтения.
- Код приложения создавай и изменяй только внутри `app/`.
- Документацию и портфолио-оформление веди в `README.md`, `docs/` и корневых файлах.
- Не изменяй `AGENTS.md`, `opencode.json` и `.opencode/` без прямого запроса.
- Не удаляй исходные файлы.
- До подтверждения плана не создавай файлы приложения.

## 4. Технологии

- Используй только HTML, CSS и современный JavaScript без фреймворков.
- Не используй npm, сборщики, CDN, внешние шрифты, внешние API и серверную базу.
- Приложение должно работать через локальный HTTP-сервер.
- Все пользовательские записи храни в IndexedDB.
- Не подменяй IndexedDB массивом в коде или `localStorage`.
- `localStorage` допустим только для небольших настроек интерфейса.

## 5. Структура файлов

- `app/index.html` — семантическая разметка приложения.
- `app/styles.css` — токены, компоненты, состояния и адаптивность.
- `app/db.js` — открытие IndexedDB, схема, миграции и операции с хранилищами.
- `app/app.js` — состояние интерфейса, рендеринг и пользовательские сценарии.
- Дополнительные JavaScript-файлы создавай только при реальной необходимости.

## 6. Схема IndexedDB

- Имя базы: `eventflow-db`.
- Версия схемы: `1`.
- Хранилище `participants`, ключ `id`, автоинкремент не использовать.
- Индексы: `email` с уникальностью, `status`, `registeredAt`, `archivedAt`.
- Хранилище `settings`, ключ `key`.
- Хранилище `activity`, ключ `id`.
- Операции, которые меняют несколько записей, выполняй одной транзакцией.

## 7. Модель участника

- `id` — UUID, создаётся приложением;
- `name` — обязательная непустая строка;
- `email` — обязательный корректный email, уникальный без учёта регистра;
- `company` — необязательная строка;
- `ticket` — одно из значений из `data/event-settings.json`;
- `status` — `new`, `confirmed`, `waitlist` или `cancelled`;
- `checkedIn` — логическое значение;
- `registeredAt` — дата в ISO-формате;
- `archivedAt` — `null` или дата архивации.

Бизнес-правило: `checkedIn: true` допустимо только для статуса `confirmed`.

## 8. Пользовательские сценарии

- Просмотр показателей: всего активных, подтверждены, пришли, лист ожидания.
- Добавление и редактирование участника через форму.
- Понятные сообщения об ошибках рядом с полями.
- Поиск по имени, email и компании.
- Фильтр по статусу и типу билета.
- Сортировка по имени и дате регистрации.
- Отметка о прибытии только для подтверждённого участника.
- Архивация вместо необратимого удаления и кнопка «Отменить» в уведомлении.
- Импорт CSV только через предпросмотр и подтверждение.
- Строки с ошибками не попадают в базу; корректные можно импортировать отдельно.
- Экспорт резервной копии в JSON.
- Восстановление JSON только после проверки файла и подтверждения замены.
- Журнал последних действий и импортов.

## 9. Визуальные правила

- Ориентируйся на `references/visual-reference.png`: светлый SaaS-интерфейс, фиолетовый основной цвет и мятные успешные состояния.
- Не копируй из референса разделы, которых нет в брифе.
- Интерфейс должен быть аккуратным на ширине 1440, 768 и 390 пикселей.
- У интерактивных элементов должны быть hover-, focus- и disabled-состояния.
- Учитывай `prefers-reduced-motion`.
- Не используй эмодзи как единственные иконки важных действий.

## 10. Безопасность учебной практики

- Не отправляй данные в сеть.
- Не добавляй аналитику, трекеры, авторизацию или облачную синхронизацию.
- Не используй реальные персональные, платёжные, медицинские или внутренние данные.
- Все опасные действия требуют подтверждения или возможности отмены.

## 11. Порядок работы

1. Изучи требования и исходные данные.
2. Подготовь план в режиме Plan и дождись подтверждения.
3. Реализуй приложение небольшими этапами в режиме Build.
4. После каждого этапа перечисли изменённые файлы и ручные проверки.
5. Не переписывай работающие части без необходимости.
6. Перед финалом проведи аудит по `references/acceptance-checklist.md`.

## 12. Публикация

- `main` — стабильная ветка по умолчанию, `develop` — интеграционная.
- Рабочие ветки — `feature/*`, `fix/*` и `docs/*`; они создаются от `develop`.
- Коммиты оформляются по Conventional Commits, сообщения — на английском.
- Релизы отмечаются тегами `vMAJOR.MINOR.PATCH` и GitHub Releases.
- CI должен быть зелёным на `main` и `develop`.
- В публичный репозиторий не попадают `.env`, токены, `*.pdf`, `*.zip`,
  `.DS_Store`, локальные отчёты и браузерные артефакты.
- `docs/examples/backup-sample.json` — синтетический пример, а не реальные данные.
